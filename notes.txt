- Code understanding:
    + execution pipeline:
        1. receive inputs: model path, image, query -> run_llava.py
        2. infer model name -> mm_utils.py
        3. load tokenizer, LM, vision tower, image processor
        4. choose inference branch (sparse or no sparse)
        5. if sparse -> replace attention module with sparse attention
        6. add special tokens, resize token embeddings, load vision tower, ...
        7. build text query string (insert image token marker)
        8. select conversation template -> final prompt -> conversation.py
        9. load image -> convert to tensors
        10. tokenize text prompt -> replace placeholder
        11. model.generate()
        12. if image in prompt -> convert to embedding
        13. project image embedding to LM hidden space
        14. replace image embedding to placeholder
        15. if sparse -> record metadata for sparse controls
        16. if sparse -> send to sparse model wrapper
        17. start autoregressive generation
        18. initial pass -> LlamaDynamicvitModel
        19. at ordinary decoder layers -> process tokens normally
        20. at specific layers, compute attention-based importance scores
        21. choose which visual tokens to keep
        22. remove / merge less important visual tokens; preserve others
        23. propagate the reduced token sequence
        24. decode next steps, use cache for faster inference
        25. compute logits, apply generation policy, append to sequence
        26. decode until EOS / max length
        27. decode final token ID to text, return model response
    + most important code files:
        1. run_llava.py -> core inference path
        2. builder.py -> core inference path
        3. llava_arch.py -> multimodal input construction
        4. sparse_llava_llama.py -> connect LLaVA with Llama backend
        5. modelling_sparse_llama.py -> sparse implementation
        6. score.py -> score visual tokens
    + most important parameters:
        1. model_path -> choose checkpoint to run
        2. dynamic_sparse -> main mode switch
        3. retained_tokens -> how many visual tokens survive pruning (192/128/64)
        4. max_new_tokens -> caps output length
        5. load_4bit / load_8bit -> memory saving load modes
        6. pruning_loc -> which decoder layers perform pruning ([2,6,15])
        7. conv_mode -> prompt formatting
- Scoring / Ranking module:
    + input:
        1. self_attn_weights
        2. v_token_start -> start of visual-token block
        3. v_token_num -> number of visual tokens
        4. text_token_start -> start of text-question block
        5. t_token_idx -> indexes of tokens used for guiding scoring
        6. layer_idx & retained_tokens -> control how agressive pruning is
    + output:
        1. mask -> 1 = keep, 0 = prune
        2. s_flag
        3. relation_vis_text -> relevance score before top-k thresholding
    + how it works:
        1. averages attention scores across heads
        2. converts selected text indices into absolute sequence positions
            2.1. before scoring, the model selects a subset of text tokens that seem most related to the image: calculate text tokens with relevance > mean relevance
        3. extracts attention from those chosen text tokens, to the current visual-token region
        4. averages over the selected text tokens -> one score per visual token
        5. chooses per-layer retention budget
        6. keeps top-k visual tokens by score

- Identifying academic gap:
    + ranking criteria:
        1. picking important text tokens from the question / prompt: computes visual-text similarity, and keep text tokens whose score is above mean
        2. score visual tokens by how much those selected text tokens attend to it -> averages self-attention weight from important question tokens to that visual token
        3. rank by that score, and then keep top-k
    + gaps following the ranking criteria:
        1. sparsevlm is currently using attention weights and averaged relevance, which indicates how the token attends to other tokens. however, whether a token is central of attention or it is directly useful for the question is a different thing. for example, man walking dog -> man is central of attention, but the prompt may be asking about the dog
        2. compositional or logical information: words such as "not", "left of", "behind", "except", "how many", ... controls how to understand the prompt, so the current criteria are missing out on these logical signals
        3. dynamic relevance: at later layers, which token is important is different - at first we might need object cues, but later on we would need to have relation / counting / ... cues
        4. diversity / coverage: missing out on redundancy, set-level diversity, multi-region coverage. it is because each visual token is independently evaluated, and top-k is selected based on their score, so many tokens would belong to the same highlighted region, lack of coverage for other regions, or many tokens have the same information
        5. no weak and critical evidence
    + importance of adding redundancy:
        1. selection is independent across tokens
        2. if many nearby patch all describe the object part, they can all score highly and crowd out other useful regions
        3. visual tokens are naturally redundant, but the current scorer has no explicit coverage terms
        4. at high compression (only retaining 64 tokens), wasting several tokens on near-duplicates is expensive
        5. coverage is important rather than patches from the same salient object
        6. lower compression -> less critical it becomes
        7. therefore, redundancy is more important than small scoring refinements, albeit less fundamental than true causal usefulness or dynamic attention / importance, but it is strong and easier to justify
        8. redundancy is strong but should not dominate relevance
    + does redundancy happen in the code?
        1. it doesn't mean the same token index is selected twice by top-k
        2. it means multiple selected visual tokens contain nearly the same information
        3. there are no steps in the code checking that

- Successfully constructed the Threshold Filtering method.
    + threshold filtering is needed because it is a simpler redundancy-aware baseline.
        . it shows whether the improvement comes from the mmr-style selection, or merely from adding any redundancy reduction.
    + threshold filtering mainly examines reducing redundancy, not performance improvement.
    + it is a secondary baseline, not the proposed method.

    + if threshold filtering performs worse, the conclusion here is that reducing redundancy helps, but a hard similarity cutoff is too crude.
        . ours is better because it balances relevance and redundancy.
    + if threshold filtering is on par with ours, we can conclude that redundancy-aware selection is a meaningful direction, and mmr is one effective formulation
        . thresholdfiltering will support that selected visual tokens should consider set diversity, not just independent relevance.
    + threshold filtering helps answer: is the gain from explicitly reducing redundant visual tokens, or from something specific to the proposed mmr scoring formula.

- Detailed implementations:
    + threshold filtering input:
        . relation_vis_text: importance score per current visual token
        . visual_states: current hidden states of visual tokens
        . layer_idx
        . retained_tokens
        . threshold_tau
        . candidate_pool_factor
    + the importance score comes from the same sparsevlm attention-based relevance signal.
    + relation_vis_text is the importance ranking used to choose the candidate pool, and then used to order tokens from most important to least important.
    + the candidate pool is the top-2k visual tokens ranked by relation_vis_text
    + we do not filter all visual tokens directly because many low-importance tokens are unlikely to be useful.
        . filtering all tokens would increase compute and may keep irrelevant patches.
    + k is the target per-layer visual-token budget for the current pruning layer.
    + k is not literally 64 or 128, although it is the config number. k is the value after _get_keep_budget(...) function.
        . k must be per-layer because sparsevlm does progressive pruning.
        . for example, retained_tokens=64 maps to layer budgets such as [66, 30, 17], not 64 at every layer.
    + cosine similarity is calculated on the current llama hidden states of the visual tokens, after image embeddings have been projected into the language model hidden space.
    + a token is discarded if its cosine similarity to any already selected token is greater than the value of tau.
    + we use the condition of similarity > tau, not >=, because tau is the strict rejection boundary.
        . a token exactly at the threshold is still allowed, avoiding agressive rejection due to floating-point equality.
    + when comparing visual tokens, we use max similarity to consider whether is should be discarded.
        . if a token is highly similar to even one selected token, it is redundant with that selected evidence.
- Details about Threshold-Fixed method:
    + threshold-fixed must allow the same per-layer token budget as the current retained_tokens setting.
        . threshold-adaptive does not backfill to the budget.
    + threshold-fixed is used in the main fixed-budget benchmark comparison.
    + it must use the same token setting with sparsevlm-original and our method in the same run because it is a controlled baseline. 
        . if threshold-fixed used more of fewer tokens, accuracy differences could come from token count, instead of selection quality.
    + if the run is retained_tokens=64, threshold-fixed is sharing the same per-layer budget schedule as ours-64 and sparsevlm-original-64, from sparse_token_dict[64].
        . same as retained_tokens=128.
    + if threshold filtering selects fewer tokens than the per-layer budget, the method fills the missing slots using backfill candidates.
    + current backfill order:
        . outside-pool tokens that pass the similarity threshold
        . outside-pool token by importance
        . remaining rejected or unselected tokens by importance
    + outside-pool tokens are prioritised because they were not rejected as redundant inside the candidate pool.
    + rejected tokens should be the final fallback because they already failed the redundancy test.
        . adding them earlier weakens the purpose of threshold filtering.
    + if backfilling contributes a lot of tokens, it suggests that the threshold is too strict, candidate pool is too small, or the image has many highly similar top-ranked visual tokens.
    + if current visual token count is less than scheduled budget, the code uses _get_keep_budget(...) which caps the budget by the visual tokens count.
    + the scorer bounds candidate size and selected count by the current visual-token count, so threshold-fixed will not over select or crash in edge cases as it can't request more tokens than exist.

- Threshold-Adaptive:
    + this method asks: what accuracy-token trade-off happens if redundancy filtering is allowed to decide the final retained count, instead of forcing a fixed budget?
    + it should not be mixed directly into the main benchmark table as a fixed-budget method because it does not control token count.
        . mixing it into the fixed-budget table would make the comparison unfair, as better accuracy might come from keeping more tokens.
    + threshold-adaptive is not truly unlimited in tokens.
        . it is still limited by the top-2k candidate pool, defined from the anchor retained_tokens setting.
    + retained_tokens=64 is only an anchor, not the final token budget since it only defines k, which defines the top-2k candidate pool size. 
    + threshold-adaptive does not include backfilling because it would turn it back to the fixed-budget method.
    + if it retains very few tokens, the threshold is very strict for that image or content, or many top candidates are highly redundant.
        . it will be judged by accuracy, which shows whether aggressive redundancy removal loses important evidence.
    + if it keeps more token than ours-64 and grants higher accuracy, we can say that it improves accuracy with a higher retained-token cost. 
        . the fair conclusion here is that if offers a different accuracy-efficiency trade-off.
    + this method must report retained token count because without it, accuracy alone is misleading.
    + additional metadata:
        . average_retained_tokens: typical token cost
        . min_retained_tokens: most aggressive compression case
        . max_retained_tokens: worst-case token cost / upper retention behaviour

- Tau:
    + tau is the cosine-similarity threshold for deciding whether a candidate visual token is too redundant with already select tokens.
    + if tau is lower (ex. 0.80), it filters more aggressively because tokens are rejected at a lower similarity level.
    + if tau is higher (ex. 0.90), it filters more leniently.
    + tau=0.85 is a middle / default setting, strict enough but not too aggressive.
